# PLAN.md — план работ (живёт в архиве, переживает сессии)

## Как работаем

1. Пользователь присылает архив (zip) с игрой.
2. Алиса читает README.md (карта файлов, правила) и PLAN.md — видит
   текущий прогресс и очередь правок.
3. Применяется РОВНО ОДНА правка из списка ниже.
4. После каждого шага плана актуализируется карта файлов в README.md —
   всегда, даже если менялся только один модуль.
5. Собирается новый zip: обновлённые модули + обновлённые README.md,
   PLAN.md и, если нужно, game_map.md. Ссылка на архив отдаётся до
   запуска каких-либо тестов, тесты — только после одобрения
   пользователя.

## Правило версии

- В шапке game_config.py стоит BUILD-маркер: `# BUILD: v5-N <название шага>`.
- N — номер последнего выполненного шага из плана. По нему Алиса
  мгновенно определяет прогресс без построчной сверки.
- Сделанные шаги вычёркиваются из этого плана (а не помечаются [x]):
  история не копится, чтобы файл не разрастался. Если что-то забыто —
  детали всегда есть в коде и комментариях к BUILD-маркеру.

## Протокол выживания файлов (важно!)

- Контейнер исполнителя пересоздаётся между сессиями: всё, что не
  прикреплено к сообщению, умирает вместе с ним — правки, собранные
  архивы, рабочие файлы. В начале новой сессии рабочая директория
  пустая, кроме архивов, присланных пользователем.
- Единственный надёжный канал передачи архива — вложение к сообщению
  (файл, созданный инструментом, автоматически прикрепляется к ответу).
  Ссылка на файл внутри контейнера живёт только до конца сессии и
  ломается после — так что ссылку давать можно только на вложение.
- Последняя доступная точка прогресса — всегда последний присланный
  пользователем архив. Прогресс не теряется никогда: сверить
  BUILD-маркер, воспроизвести шаг по плану за один заход (он
  самодостаточен), пересобрать архив и прикрепить.
- Страховочные сохранения: сразу после каждой успешной партии замен
  пересобирать архив и сохранять его на диск — файл автоматически
  прикрепляется к результату вызова инструмента и живёт в переписке,
  как присланное вложение. Тогда обрыв контекста посреди шага не
  теряет работу: последнее сохранение уже прикреплено, остаётся
  воспроизвести только хвост шага.
- Итоговый архив шага собирается СТРОГО в последнем вызове
  инструмента перед ответом пользователю. Промежуточные файлы,
  созданные посреди хода, не доживают до клика пользователя —
  проверено потерянными сборками r6, r7 и draft-срезами.
- Ссылка на файл в ответе даётся ТОЛЬКО в формате
  [имя](doc=идентификатор_из_результата_инструмента). Ручные URL
  (gproxy и прочие) запрещены — они не работают.
- При вынужденной остановке (лимит контекста): не пересобирать архив
  заново, если он уже был сохранён после последней партии замен, —
  он уже прикреплён. В докладе честно указать, какая партия замен
  была последней сохранённой, а какая применена только в коде.

## Целевая платформа: только Android

Игра существует только как APK. ПК-режим не поддерживается и не
тестируется: код окон, ресайза и клавиатуры ПК постепенно удаляется,
а не адаптируется. Ключевая цель всех текущих правок — игра должна
летать без тормозов на слабом телефоне. Любая правка проверяется
вопросом «что это даст телефону», а не «как это будет на ПК».

## Список правок

1. [x] Лавка улучшений мигает, когда ни одного улучшения недоступно:
   панель «АПТЕЧКА» не влезает в выдвинутую лавку (низ на 910 px при
   пределе 886 px при SHOP_H = 970), но any_upgrade_affordable()
   учитывает её цену. Поднять SHOP_H до 1000 и учесть в подсветке
   только реально видимые панели. Файлы: game_config.py (SHOP_H),
   game_shop.py (предел), game_economy.py (any_upgrade_affordable).

   ширина панели считается по заголовку (pw = max(S(460), ширина + 2*S(24))),
   кэш панели по ширине (_notice_panel_w, в кадре ничего не строится).
   Файл в плане назван приблизительно: панель в game_effects.py, а
   подпись ставится в game_digging.py (как было с компасом).

   next_level() обнуляет всё, кроме energy_time и clover_time.
